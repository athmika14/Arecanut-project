  SECTION 7 — Filename Reliability for Source-Group Reconstruction
────────────────────────────────────────────────────────────────────────

  QUESTION: Can we reliably reconstruct which derived images belong
  to the same original source using filenames alone?

  VERIFIED:
  1. Every file in every partition matches the pattern
        <class>_original_<source_id>_<UUID>.jpg
     with zero exceptions.  This is 100% reliable.

  2. Source IDs fall into two categories:
       Numeric IDs  (e.g. 510, 7191) — simple integers.
       Camera IDs   (e.g. IMG_20230819_174511) — Android camera
                    filenames encoding date and time.
     Both types are unambiguous unique identifiers for the original.

  3. MD5 hashes CONFIRM (Section 4) that files sharing a source_id
     but different UUIDs have distinct pixel content.  They are
     genuinely separate augmented copies, not bit-for-bit duplicates.
     (Within-partition exact-hash duplicates found in the prior audit
     are a separate anomaly — see note below.)

  4. The class label encoded in the filename always matches the
     containing folder name.  No mislabelled files were found.

  UNCERTAIN CASES flagged:

  U1. WITHIN-PARTITION EXACT DUPLICATES (from prior audit):
      343 hash-duplicate groups exist within TRAIN and 39 within TEST.
      Some of these share the same source_id; others have DIFFERENT
      source_ids but identical pixel content.  Example from audit:
        Mahali_Koleroga_original_7311.jpg_... and
        Mahali_Koleroga_original_7312.jpg_...
      These are DIFFERENT source IDs producing an identical image.
      This means source_id is NOT always sufficient to identify
      the unique original; two numeric IDs can point to visually
      indistinct photographs.  ESTIMATE: affects a small fraction
      (<5%) of sources; cannot be fully resolved without the original
      photographs.

  U2. NUMERIC ID AMBIGUITY:
      Numeric IDs like '510' and '5100' or '51' could theoretically
      collide if parsed by prefix matching.  The regex-based parser
      used here extracts the full token between '_original_' and
      the UUID, so '51' and '510' are treated as distinct.  This
      is verified correct by examining the actual filenames.

  U3. CROSS-CLASS SOURCE RE-USE:
      No evidence of the same source_id appearing in multiple classes.
      Each source_id is scoped to a class folder, so re-use across
      classes is not structurally possible.  CONFIDENCE: HIGH.

  CONCLUSION:
  Filenames provide SUFFICIENT information to reconstruct source groups
  for the purpose of a leakage-safe split.  The one caveat is U1:
  a small number of visually identical images carry different source_ids,
  meaning a purely filename-based grouping will not catch every pixel-
  level duplication.  For an MCA project this is acceptable; for a
  publication-grade split, a hash-based deduplication pass should be
  applied first.

  SECTION 8 — Recommended Leakage-Safe Group-Based Split
────────────────────────────────────────────────────────────────────────

  PROBLEM WITH THE EXISTING SPLIT:

  The existing split was done at the augmented-image level, NOT at
  the source-image level.  The result:

    Total unique sources in dataset        : 1226
    Sources contaminating train<->test     : 1033  (84.3% of all sources)
    Sources contaminating any two partitions: 1160  (94.6%)
    Sources that are fully partition-safe  : 66  (5.4%)

  THE CORRECT APPROACH — Group-Stratified Split:

  Step 1 — Build source groups.
    For each class, list all unique source_ids from ALL three
    partitions combined.  Each source_id is one group.

  Step 2 — Split at the GROUP level, not the image level.
    Assign each source_id to exactly one of: train / val / test.
    Then all derived images of that source go to the same split.
    Suggested ratio (applied to source groups):
      Train : 70%  of source groups
      Val   : 15%  of source groups
      Test  : 15%  of source groups

  Step 3 — Stratify by class.
    Apply the 70/15/15 group split independently per class so
    every class is proportionally represented in every partition.

  Step 4 — Use a fixed random seed (e.g. 42) for reproducibility.

  Step 5 — Deduplicate within groups (optional but recommended).
    Remove exact-hash duplicates before finalising the split.
    This eliminates the U1 uncertainty described in Section 7.

  using source_id as the grouping key per class.
