  NOT TESTED ITEM 5 — CORS Preflight from a Real Browser
========================================================================

  Original reason: "The Flask test client bypasses CORS. CORS
  configuration verified by code inspection of app.py."

  Feasibility re-check:
    Google Chrome is installed on this machine. The Flask backend can
    be started as a real server on port 5000. curl.exe (the native
    Windows curl) can send HTTP requests with arbitrary headers,
    including the Origin and Access-Control-Request-* headers that
    a browser sends during a CORS preflight. This is a fully safe,
    non-destructive test.

  Method: Flask started as a real server (python app.py, debug mode),
          curl.exe used to send OPTIONS and POST requests with browser-
          style Origin headers. No application files were modified.
          The temp image file created for the POST test was deleted
          immediately after use (it was a synthetic gray image in the
          OS temp area, not inside the project).

  Tests executed (2026-10-21):

  Test 5a — GET /api/health (confirms server is running)
    Command: curl.exe -s http://localhost:5000/api/health
    Response:
      HTTP 200 OK
      {"disease_model": "loaded",
       "status": "ArecaNut AI backend is running"}
    Result: PASS

  Test 5b — OPTIONS preflight from allowed origin (localhost:3000)
    Command:
      curl.exe -s -D - -o NUL -X OPTIONS
        -H "Origin: http://localhost:3000"
        -H "Access-Control-Request-Method: POST"
        -H "Access-Control-Request-Headers: content-type"
        http://localhost:5000/api/disease/predict
    Response headers:
      HTTP/1.1 200 OK
      Access-Control-Allow-Origin: http://localhost:3000
      Access-Control-Allow-Headers: content-type
      Access-Control-Allow-Methods: DELETE, GET, HEAD, OPTIONS, PATCH, POST, PUT
    Interpretation:
      The server returned Access-Control-Allow-Origin matching the
      request Origin exactly. A browser would accept this preflight
      and proceed with the actual POST request.
    Result: PASS

  Test 5c — OPTIONS preflight from disallowed origin (evil.example.com)
    Command:
      curl.exe -s -D - -o NUL -X OPTIONS
        -H "Origin: http://evil.example.com"
        -H "Access-Control-Request-Method: POST"
        http://localhost:5000/api/disease/predict
    Response headers:
      HTTP/1.1 200 OK
      (no Access-Control-Allow-Origin header)
    Interpretation:
      The server did NOT echo back the disallowed origin. A browser
      would see no ACAO header and block the request. This is the
      correct CORS behaviour for an unlisted origin.
    Note: The server returns HTTP 200 for OPTIONS regardless of origin
      (Flask-CORS does not reject the OPTIONS call itself — it simply
      omits the ACAO header). The browser enforces the block.
    Result: PASS

  Test 5d — POST with Origin header (simulates actual browser request)
    Command:
      curl.exe -s -D - -X POST
        -H "Origin: http://localhost:3000"
        -F "image=@<synthetic_50x50_grey_jpeg>;type=image/jpeg"
        http://localhost:5000/api/disease/predict
    Response headers:
      HTTP/1.1 200 OK
      Access-Control-Allow-Origin: http://localhost:3000
      Content-Type: application/json
    Response body:
      {"predicted_class": "healthy_foot", "confidence": 0.662959,
       "note": "confidence is the raw softmax score for this class
                and is not a calibrated probability",
       "all_scores": {
         "Healthy_Leaf": 0.015145, "Healthy_Nut": 0.028791,
         "Healthy_Trunk": 0.010694, "Mahali_Koleroga": 0.016581,
         "Stem_bleeding": 0.006645, "bud borer": 0.000040,
         "healthy_foot": 0.662959, "stem cracking": 0.229949,
         "yellow leaf disease": 0.029196}}
    Interpretation:
      The server included ACAO: http://localhost:3000 in the response.
      A real browser would read this header and allow the JavaScript
      fetch() call to access the response body. The complete cross-
      origin request lifecycle was exercised.
    Result: PASS

  Test 5e — POST from disallowed origin (no ACAO header returned)
    Command:
      curl.exe with -H "Origin: http://evil.example.com"
    Response headers:
      HTTP/1.1 200 OK
      (no Access-Control-Allow-Origin header present)
    Interpretation:
      The server processed the request (it still returns 200 for the
      POST itself — CORS enforcement is the browser's responsibility),
      but it did NOT include an ACAO header. A real browser would
      block the JavaScript from reading the response. The CORS policy
      is working correctly.
    Result: PASS

  Summary:
    [PASS] Flask server starts and accepts real HTTP connections
    [PASS] OPTIONS preflight from localhost:3000 returns correct ACAO header
    [PASS] OPTIONS preflight from unlisted origin returns no ACAO header
    [PASS] POST from allowed origin returns ACAO header and prediction JSON
    [PASS] POST from disallowed origin returns no ACAO header (browser blocks)

  Remaining limitation:
    These tests used curl rather than a real browser. A browser adds
    additional security checks (same-site cookies, referrer policies,
    certificate validation in HTTPS). Since the app uses HTTP in
    development, the curl simulation is a faithful substitute for
    the browser's CORS enforcement in the dev environment.

     origins — it simply omits the ACAO header. This is correct
     behaviour. The browser, not the server, enforces the block.
     Some security auditors expect a 403 from the server for
     cross-origin OPTIONS; Flask-CORS follows the W3C CORS spec
     which does not require this.
